# 0009: klt pin and the item-1 attestation binding

- **Status**: proposed
- **Date**: 2026-11-15
- **Decided by**: builder agent, from issue #142 (pending human ratification)

## Context

The committed T1 attestation envelopes and the verdict of record
(`manifests/gf180-jpeg-codec.signoff.json`) were generated with klt 0.8.0,
while the fleet's workers carry moving 0.9.x dev builds. Running a 0.9.x
`klt signoff --attest 1 --check` against the committed item-1 envelope
reports `status: drifted` (exit 3), even though the design is unchanged.
Issue #142 measured this drift on 2026-11-15 and verified its cause in klt
source: klayout-tools#4764 ("signoff --attest does not bind inventory
members: manifest render stays 'met' after a source edit", closed
2026-11-01) deliberately changed item 1 to bind its **whole input set** —
`provenance.input.paths` (one `{path, content_hash}` per member, 24 files
here) plus a combined `input_set_digest` — where 0.8.0 bound only the
inventory file itself. The committed 0.8.0 envelope therefore carries an
item-1 citation that cannot detect a design-source edit: appending a line to
an RTL file still grades item 1 `met`. A T1 "design sources" citation blind
to its own sources is not evidence (CLAUDE.md: verification is the product;
recorded results are append-only evidence).

The envelope `schema_version` is `1` in both shapes — an incompatible
`provenance.input` shape change inside an unchanged schema version, with no
migration path and no version-tolerant `--check`
(2AMLogic/klayout-tools#5829). Consequence: a refreshed 0.9.x-shaped
envelope and a CI pinned at 0.8.0 fail each other's `--check` in both
directions, so the pin bump and the evidence refresh must land in one
change.

## Decision

- klt is pinned to the PyPI release **0.9.2**
  (`.github/workflows/signoff.yml`, `manifests/README.md`, `README.md`).
  Releases pin, dev builds do not: the host tool moved 0.9.2.dev1029 →
  0.9.3.dev3 within one day of this issue being filed, and CI can only
  `pip install` a release.
- The item-1 envelope (`manifests/attest/item1.json`) is regenerated under
  0.9.2, and the manifest's item-1 `content_hash` updated to the envelope's
  new combined input-set digest. The verdict of record is regenerated under
  the same pin (`signoff.yml` byte-compares it; the record's `build` block
  embeds the tool identity, so the record must be generated by the
  CI-pinned version, not by a host dev build — use
  `uvx --from "klayout-tools==0.9.2" klt …`, never the host `klt`).
- Items 9 and 10 need no regeneration: their envelopes bind the inventory
  file alone in both shapes, `provenance.input` is unchanged for them, and
  `klt_version` is not part of the `--check` comparison (measured: a 0.9.2
  `--check` accepts the committed envelopes).

## Alternatives considered

- **Pin at 0.8.0 and write only this record** (issue #142's original
  option 1). Cheapest, and CI already pinned it — but it knowingly keeps an
  item-1 citation that is blind to a design-source edit, and leaves every
  agent re-discovering the same `drifted` report against the host tool.
- **Accept the envelope-shape drift and document it** (option 3). Refuted:
  the shape change is intentional (#4764), `--check` is designed to flag
  it, and `signoff.yml`'s attest steps have no exit-code tolerance, so
  "accepting" the drift would weaken the CI gate.
- **Pin to the host build (`0.9.3.dev3+…`)**. Not on PyPI, so CI cannot
  install it; a dev build is not a reproducible pin.
- **Regenerate the gate-level netlist too.** Unnecessary:
  `flow/synthesize.sh --check` (the inventory's freshness command) already
  passes; refreshing the envelope does not run synthesis.

## Consequences

- Item 1's citation now covers every input-set member. Editing any of them
  — any `rtl/*.v` file, `flow/synthesize.json`, `flow/sram_blackbox.v`, or
  the netlist — grades item 1 `stale_evidence` until the envelope, the
  manifest row's `content_hash` and the record are all regenerated **in the
  same PR** (procedure in `manifests/README.md`). That is the point of the
  change, and its one real cost.
- The recorded T1 verdict does not move: `t1_met_count` stays 3, item 1
  stays `met`, and every item status is unchanged; the intentional
  differences are the record's `build` block and item 1's citation hash.
- Envelopes generated by adjacent klt releases remain mutually
  un-checkable (`schema_version` unchanged; 2AMLogic/klayout-tools#5829):
  any future pin bump must regenerate every affected envelope and the
  record in the same change as the bump.
- A re-pin is a new decision record (precedent: 0001, and the 0.8.0 bump in
  PRs #49/#50), together with the evidence refresh it forces.
